# MathEye 技术选型评估报告

> 日期：2026-08-25
> 状态：评估阶段（非实施规范）
> 目标形态：Web 应用 · AI 能力基于云端 LLM API

## 1. 产品愿景

一个全年龄段的数学学习 AI 应用：

- 可执行 LaTeX 表达式，沙箱运行代码，动态绘制函数图像
- AI 答疑，并结合用户当前水平调整回答方式
- 基于知识点构建并持续重组知识图谱，高亮"当前可学习"的知识点
- 数学研究者可将其视为游戏；同时适配儿童到成人全年龄段

## 2. 整体架构

```
┌─ 前端 (React / Next.js) ───────────────────────┐
│  KaTeX 渲染 │ 动态图像 │ 图谱可视化 │ 答疑对话 │
│  Pyodide 沙箱（浏览器内执行用户代码）           │
└──────────────────┬─────────────────────────────┘
                   │ REST / WebSocket
┌─ 后端 (Python FastAPI) ───────────────────────┐
│  答疑编排服务 │ 水平模型引擎 │ 图谱服务        │
│  SQLite/Postgres │ LLM API 网关               │
└───────────────────────────────────────────────┘
```

选型理由：后端 FastAPI 与项目 Python 技术栈一致，且 AI 生态
（SymPy、embeddings、各 LLM SDK）在 Python 中最成熟。

## 3. 子系统技术选型

### 3.1 LaTeX 渲染与符号计算

**结论：KaTeX + SymPy**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **KaTeX + SymPy（选定）** | KaTeX 渲染极快；SymPy 免费自托管，支持求解/化简/微积分 | 复杂计算慢于商业 CAS |
| MathJax | 兼容性最全 | 渲染慢，交互场景卡顿 |
| Wolfram API | 计算能力最强 | 昂贵，有调用限额 |

关键设计：**渲染与计算分离**。

- KaTeX 只负责显示；
- "执行 LaTeX 表达式"由前端将 LaTeX 解析为表达式树（LaTeX parser 或由 LLM 转 SymPy 代码），交给沙箱执行；
- 所有数学结论必须经 SymPy 计算验证后再展示给用户。

### 3.2 代码沙箱

**结论：MVP 用 Pyodide（WASM）完全跑在浏览器内；后续按需加服务端沙箱兜底。**

| 方案 | 安全性 | 延迟 | 成本 |
|---|---|---|---|
| **Pyodide（WASM，浏览器内）（选定）** | 天然隔离 | 首次加载 ~10MB 后秒开 | 免费 |
| 服务端容器（Docker/gVisor per-user） | 强 | 冷启动延迟高 | 服务器费用 |
| WASM + 服务端兜底混合 | 最强 | 最优 | 中等 |

收益：砍掉 MVP 阶段几乎全部沙箱运维成本。数值计算、绘图数据生成
在 Pyodide 中足够用。

### 3.3 动态函数图像

**结论：JSXGraph 或 function-plot**

| 方案 | 特点 |
|---|---|
| **JSXGraph / function-plot（选定）** | 开源免费，缩放拖拽、参数滑动条，易与 LaTeX 输入联动 |
| Desmos API | 体验最好，但商用需授权协议，深度绑定其生态 |
| Plotly | 适合统计图，函数动态交互不如前两者 |

### 3.4 AI 答疑（结合用户水平）

核心是**答疑编排层**而非单纯调 API：

1. **上下文组装**：将 `当前知识点 + 用户掌握度画像 + 近期错题 + 目标年龄段语风` 注入 system prompt；
2. **苏格拉底式分级**：同一引擎不同 prompt 模板——儿童模式给提示不给答案，研究者模式直接讨论证明思路；
3. **结构化输出**：LLM 返回 JSON（答案、涉及知识点 ID、难度评级），供自动更新水平模型与图谱；
4. **成本控制**：确定性计算走 SymPy，不消耗 LLM tokens；LLM 只负责解释与引导。

### 3.5 知识图谱（应用脊柱）

| 层 | 选型 |
|---|---|
| 存储 | **SQLite（MVP）/ Postgres** 存节点表 + 边表；Neo4j 仅在图谱超万节点时考虑 |
| 可视化 | **Cytoscape.js**（支持高亮、布局算法）；备选 React Flow |
| 自动重组 | LLM + embeddings：新知识点 → 向量化 → 相似节点检索 → LLM 提议边关系 → **人工确认后入库**（禁止全自动写入） |
| 高亮逻辑 | 规则引擎而非 LLM：前置节点掌握度 ≥ 阈值 → 标记"可学习"；多路径可达时按「解锁收益 / 难度」排序推荐 |

答疑、推荐、游戏化进度全部挂在图谱节点上——图谱是整个系统的骨架。

### 3.6 用户水平模型

分阶段演进，避免过早引入复杂模型：

- **阶段 1**：每节点一个 mastery 分（0~1），答题对错用 Elo 式更新（简单、可解释、够用）
- **阶段 2**：BKT（贝叶斯知识追踪）或 DKT，处理遗忘曲线与间隔复习

**全年龄段适配策略**：同一图谱的分层内容包——同一知识点挂不同难度的题目和讲解，
而不是维护两套系统。

## 4. 游戏化设计要点

- 图谱呈现为**技能树/迷雾地图**：未学区域半遮蔽，可学习节点发光——天然的探索感
- 面向研究者的内容：**证明挑战**、**构造反例**类任务（部分构造可由 SymPy 自动验证）
- 不做排行榜（对成人无效）；核心是**进度可见性 + 解锁感**

## 5. 数据模型草案

```sql
-- 知识点
knowledge_node (
  id, title, description,
  difficulty_tier,        -- 分层难度
  embedding BLOB          -- 用于相似检索
)

-- 先修关系（有向边）
knowledge_edge (
  from_node_id, to_node_id,   -- from 是 to 的先修
  weight,
  status                      -- confirmed / proposed（LLM 提议待确认）
)

-- 用户掌握度
mastery (
  user_id, node_id,
  score REAL,             -- 0~1
  updated_at,
  attempt_count
)

-- 学习事件（水平模型的原始数据）
learning_event (
  id, user_id, node_id,
  event_type,             -- answer_correct / answer_wrong / hint_used / ...
  payload JSON,
  created_at
)
```

## 6. 核心 API 草案

```
GET  /api/graph?user_id=            # 图谱 + 该用户的高亮状态
GET  /api/nodes/{id}                # 知识点详情（含分层内容）
POST /api/events                    # 上报学习事件，触发 mastery 更新
POST /api/tutor/chat                # 答疑（服务端组装画像上下文后调 LLM）
POST  /api/compute                  # 符号计算代理（SymPy，用于前端无法完成的运算）
POST /api/graph/review              # LLM 提议的边关系人工审核接口
```

## 7. 实施路线图

| 阶段 | 内容 | 验证目标 |
|---|---|---|
| P1 | 图谱骨架 + mastery 模型 + 高亮推荐 | 核心学习循环是否成立 |
| P2 | KaTeX + Pyodide 沙箱 + 动态图像 | 交互体验是否达标 |
| P3 | LLM 答疑（注入画像）+ 自动更新掌握度 | 答疑质量是否可接受 |
| P4 | LLM 辅助图谱重组 + 游戏化层 | 用户留存表现 |

每个阶段独立可交付，严格按序推进。

## 8. 风险清单

1. **LLM 数学幻觉**：所有数学结论必须经 SymPy 验证后再展示；LLM 只做解释不做判定。
2. **图谱冷启动**：初期知识库需人工/半人工构建；建议从单一领域起步（如初中函数或线性代数）。
3. **范围蔓延**：六个子系统并行必然失败；坚持 P1→P4 顺序。
4. **Pyodide 体积**：首屏加载约 10MB，需懒加载与缓存策略。
5. **LLM 成本失控**：结构化任务尽量走规则引擎与 SymPy，LLM 仅用于解释、引导与图谱提议。
