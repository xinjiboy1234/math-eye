# MathEye Avalonia 方案评估

> 日期：2026-08-26
> 状态：评估阶段
> 上游文档：[Electron 评估](./2026-08-26-math-eye-electron-evaluation.md)、[技术选型评估报告](./2026-08-25-math-eye-tech-evaluation.md)
> 议题：以 Avalonia（C#/.NET XAML）替代 Electron 作为桌面框架。

## 0. 结论先行

**不推荐。** 对「设置面板型」桌面应用，Avalonia 的架构优雅度和资源占用确实优于 Electron；但 MathEye 是一个**渲染密集、可视化密集**的产品（公式排版、图谱迷雾地图、动态函数图像），它的五大 UI 子系统里有三个的最佳实现只存在于 JS 生态。选 Avalonia 不是换框架，是把三块核心体验从「接库」变成「自研」。

用户的直觉「整体感好，但 UI 代价可能大」是对的——下文把这个代价量化。

## 1. 五大 UI 子系统逐项对照

| 子系统 | Web/Electron 方案 | Avalonia 方案 | 代价评估 |
|---|---|---|---|
| 数学排版 | **KaTeX**（天级接入） | 无成熟等价物：XamlMath 渲染质量与覆盖面远逊且维护弱；或内嵌 WebView 只为渲染公式（架构自我否定）；或 SkiaSharp 自研 LaTeX 引擎（月级工程） | 🔴 高 |
| 知识图谱 | **Cytoscape.js**：力导向布局、迷雾遮蔽、呼吸动画、高亮全现成 | MSAGL 年代久远无游戏化交互；GraphX 已死；实际等于用 SkiaSharp 自研力导向布局引擎 + 交互层 | 🔴 很高（3–6 周起步） |
| 动态函数图像 | **JSXGraph/function-plot** | ScottPlot/OxyPlot 可覆盖约七成；参数滑动条联动可行 | 🟡 中 |
| 答疑对话 | markdown + 行内 LaTeX 渲染组件现成 | Avalonia 缺少成熟的「markdown 内嵌公式」控件，需自定义组合控件 | 🟡 中 |
| 沙箱面板/UI 壳 | 标准 Web 组件 | 标准桌面组件 | 🟢 低（持平） |

关键认知：**产品的 UI 复杂度存在于领域可视化本身，框架不能消除它，只能决定它是「接线」还是「造轮子」。** Web 生态恰好把这三大件做成了库。

## 2. 更深一层的结构性问题：双运行时问题反而恶化

Electron 评估里否决 Python sidecar 的前提是 **Pyodide 承担了全部数学计算**。Avalonia 下此前提消失：

1. **SymPy 没有可用的 C# 替代**（Math.NET Symbolics 远不足以做 solve/integrate），「所有数学结论经 SymPy 验证」的不变量迫使应用必须携带真实 Python 运行时；
2. 于是安装包 = Avalonia 自包含发布（~80–150 MB）**加上** Python 运行时（embeddable dist 或 PyInstaller，+40–60 MB）——体积优势相对 Electron 基本蒸发，却背上了进程管理、启动时序、三平台打包矩阵的复杂度；
3. 最严重的是**沙箱退化**：Pyodide 在浏览器 WASM 里天然隔离用户代码；换成真实 Python 后，用户代码和 SymPy 服务同进程运行是不可接受的安全模型，必须额外构建 OS 级进程隔离——把原本免费的东西重新花钱买。

## 3. BYOK 与同步：两方案打平

这部分 Avalonia 毫无劣势也毫无优势——`HttpClient` 直连厂商、DPAPI/Keychain 存 key、SQLite、同步客户端逻辑，C# 与 TypeScript 实现成本相同。既然分不出胜负，决策权重完全落在 §1 的 UI 生态上。

## 4. 「整体感」的反驳

整体感应来自设计系统纪律（design tokens、统一组件库、主题规范），而非框架本身。反例与正例都足够多：Electron 应用可以精致（VS Code、Figma 桌面端、Linear），原生应用也可以割裂。对本产品还有一个特殊因素：**KaTeX 的排版本身就是最强的视觉识别**，应用的「数学质感」由它定义——而这恰恰是 Avalonia 给不了的。Web 路线下，shadcn/ui + tokens 即可获得一致的整体感。

## 5. 其他因素

- **AI 结对开发效率**（本项目 Codex-first 工作流的现实约束）：主流编码代理对 React/TS 的生成质量显著高于 Avalonia XAML + C#，UI 迭代速度差距会被工作流放大。
- **性能**：Avalonia 内存占用确有优势（~150–250 MB vs Electron ~400–600 MB）。这是它最真实的加分项，主要利好老旧学校机房。但注意 Pyodide 换真实 Python 后差距收窄。
- **技能栈**：若团队 C# 强于 TS，此项应上调 Avalonia 权重；仅就本仓库现状（前端资产与测试用例均为 TS/pytest 可平移形态）不构成理由。
- **何时应重估 Avalonia**：产品形态转向「内容管理后台」「题库录入工具」这类表单密集型界面，或放弃图谱可视化核心时。届时它会是更好的选择。

## 6. 决策矩阵（合并 Electron 评估结论）

| 判据（按权重排序） | Electron 本地优先 | Avalonia |
|---|---|---|
| 三大可视化子系统落地成本 | 库级接入 ✅ | 自研轮子 ❌ |
| 数学排版质量（产品视觉核心） | KaTeX ✅ | 无等价物 ❌ |
| 用户代码沙箱安全性 | WASM 天然隔离 ✅ | 需自建 ❌ |
| 安装包/内存 | 中 ⚠️ | 中（含 Python 后打平）⚠️ |
| BYOK/同步实现成本 | ✅ | ✅ |
| AI 辅助开发效率 | ✅ | ⚠️ |

## 7. 建议

1. 维持上一份评估的结论：**Electron + 本地优先 + BYOK**。Avalonia 的「整体感/轻量」优势被三大可视化子系统的高昂重建成本和双运行时恶化完全抵消。
2. 若动机是「担心 Web 技术栈复杂」：注意 Tauri 共享同一套 Web 前端，同样解决不了此顾虑；而真正的复杂度在领域可视化，任何框架下都要面对，区别只在谁替你承担（生态库 vs 你自己）。
3. 若动机是内存占用：先在 P1 用 Electron 出原型实测低端机表现（§5 风险 5），数据说话后再考虑是否值得为此付出 §1 的代价——预判是不值得。
